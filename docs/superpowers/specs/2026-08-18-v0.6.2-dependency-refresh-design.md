## Goal

Release `v0.6.2` with current supported packages, toolchains, CI actions, and
interop peers while retaining GoBGP `v3.37.0`, the final v3 release. The release
also corrects public claims that the independent RFC review disproved. It does
not add new BFD behavior.

Local Go quality tooling runs through the pinned dev container rather than on
the shared host. The service has a default cgroup quota of 4 CPUs, an 8 GiB
hard memory limit with no additional swap, a 4 GiB reservation, and 1,024
PIDs. Go 1.27 derives `GOMAXPROCS` from the CPU quota; `GOMEMLIMIT=6GiB` leaves
non-Go-runtime headroom below the hard limit. golangci-lint additionally uses
`run.concurrency: 4`, its prebuilt image binary, and disposable container-local
Go and linter caches. The final dev stage includes `gcc` and `libc6-dev`, which
provide the cgo toolchain required by Linux `go test -race` without runtime
package installation. It sets the absolute `GOBIN=/go/bin` and includes
`/go/bin` in `PATH`, so every pinned command built with `go install` shares the
same discoverable location as the prebuilt golangci-lint binary. `make lint` is
the supported local entrypoint;
`make lint-ci` is an inner container-only CI contract and fails before starting
the tool when invoked on the host.

The dev image contains no `@latest` installs. `scripts/vuln-audit.go` uses the
Go 1.26 typed `errors.AsType[*exec.ExitError]` API. Tool dependencies move to a
separate `tools/go.mod`; the Go `tool` directive alone does not isolate tool
modules from the main module's Minimal Version Selection graph. Root Make and
CI wrappers invoke the pinned tools through that tools module. The controlled
audit scans `go.mod` and `tools/go.mod` as two explicit OSV inputs and retains
separate raw JSON reports. CI also generates separate CycloneDX JSON SBOMs from
the two module files with Syft `v1.51.0`; tool dependencies are never folded
into the runtime vulnerability or SBOM artifact.

## Vulnerability policy

The Go vulnerability database reports `GO-2026-4736` against GoBGP v3 and v4
without a fixed release. The existing exception expired on 2026-07-31, so the
release remains red until maintainers make a separate recorded security
decision. The approved exception permits exactly this advisory through
2026-09-30; it may not be silently renewed or broadened. Every other finding
fails the build.

The mitigation is routing-plane specific: explicit trusted BGP peers,
control-plane ACLs or GTSM where applicable, and gobgpd monitoring/restart.
Securing the management gRPC endpoint remains required but does not mitigate a
NEXT_HOP parser denial of service on TCP/179.

## Documentation truth correction

`v0.6.2` immediately corrects claims that are not supported by the current
implementation. This is documentation repair, not protocol expansion.

- RFC 5880 becomes “asynchronous core, partial”. Known blockers include
  outgoing Poll/timer semantics, remote Demand handling, diagnostic ordering
  and errata, and acknowledged AdminDown; the list is not treated as exhaustive
  until every stable gate in the v1 contract passes.
- RFC 5883 documents the current one-transit-hop TTL restriction instead of
  attributing `TTL >= 254` to the RFC.
- RFC 9384 is “not implemented; blocked by GoBGP API” because the wire subcode
  is Administrative Shutdown `/2`, not BFD Down `/10`.
- RFC 9468, RFC 9747, RFC 7130, RFC 8971, and RFC 9521 are marked preview or
  experimental with their exact limitations.
- RFC 9764 is not called complete for authenticated padded packets until the
  combined mode passes.
- The 16M packets/s figure is labelled a microbenchmark of unmarshal, demux,
  and channel delivery, not end-to-end UDP processing or a scale guarantee.
- The 10,000-session production narrative is removed. No supported scale is
  claimed from discriminator lookup benchmarks alone.
- The current all-interface plaintext management and metrics listeners and the
  unauthenticated flight-recorder endpoint are documented as unsafe defaults.
  Until v1 changes the runtime contract, deployment guidance must bind them to
  loopback or an isolated management namespace and keep debug exposure off.

English is the source; existing Russian counterparts receive the same factual
changes before release.

## Python 3.14.7 uv island

Repository-owned Python is constrained to the containerlab bootstrap and the
optional Scapy fuzzer. One root `pyproject.toml` and `uv.lock`, with
`.python-version` fixed to 3.14.7 and `tool.uv.required-version` fixed to
0.12.6, replaces every pip, pipx, and independent `uv tool` installation.

The single resolution has three non-default groups:

- `peer`: Scapy 2.7.0;
- `runtime`: intentionally empty after the Compose provider migration;
- `quality`: Ruff 0.16.4, ty 0.0.74, Bandit 1.9.4, yamllint 1.38.0,
  junit2html 31.1.4, and pip-audit 2.10.1.

CI downloads uv 0.12.6 from its exact GitHub release asset and verifies the
amd64 or arm64 SHA-256 before installation. Containerfiles copy uv and Python
from immutable multi-platform OCI indexes. All repository Python entrypoints
use `uv run --frozen`; CI and images use `uv sync --frozen`. ExaBGP remains a
separate immutable external peer and is not duplicated in this lock.

The containerlab bootstrap validates both initial and redirected request
targets and permits only the exact `api.github.com` and `github.com` hosts over
HTTPS. Every subprocess uses an argument vector with shell execution disabled,
and its executable is resolved to an absolute path only after matching the
checked-in command allowlist. Ruff and Bandit suppressions for those
standard-library boundaries are limited to the exact validated call sites;
the project configuration has no broad URL or subprocess exclusions.

## Podman Compose provider

Python `podman-compose` is replaced by the official Docker Compose `v5.5.0`
standalone Go binary. GitHub GraphQL reports `docker/compose` active and
unarchived; `v5.5.0`, published 2026-08-17, is the latest stable release. The
provider is installed from the official amd64 or arm64 release asset only
after its embedded SHA-256 is verified. CI exports the installed absolute path
through `PODMAN_COMPOSE_PROVIDER`; the development image installs the same
binary at `/usr/local/bin/docker-compose` and sets that path explicitly.

Every repository invocation uses `podman compose`, never the provider binary
directly. This retains Podman's socket discovery and environment setup while
preventing fallback to Python `podman-compose`. Provider warning banners are
disabled with `PODMAN_COMPOSE_WARNING_LOGS=false`; version gates still print
and require exact Docker Compose `v5.5.0` diagnostics.

The `dev-ensure` preflight discovers the `dev` service through project-scoped
`podman compose ps --all --quiet dev` output and then inspects its immutable
container ID. It never derives a container name from legacy Compose naming.
Benchmark result-mount validation decodes the canonical `compose config` YAML
and requires one `bind` mount from the configured absolute result directory to
`/results`, with `selinux: z`, on each benchmark service. It does not depend on
whether Compose renders equivalent short or long volume syntax.

Docker Compose v5 removed its internal BuildKit builder and delegates BuildKit
work to the external Buildx/Bake plugin. GoBFD does not add Docker or Buildx to
the Podman runtime. Podman-backed Compose builds therefore set
`DOCKER_BUILDKIT=0` and use Compose v5's retained classic Docker API build path,
which talks to the Podman compatibility socket. This choice must be covered by
an actual bounded image build, not only `compose config` or dry-run output.

The uv `runtime` group remains present but empty so the single-lock group
contract stays stable. No Python package is installed to provide Compose. All
11 tracked Compose files must render through the pinned provider, including
the required e2e-core fixture variables, before any live topology gate runs.

## Change-set boundaries

The release is split into independently reviewable local commits:

1. Go toolchain and runtime module closure.
2. YAML module path and native HTTP/2 compatibility edits.
3. Isolated developer-tool module and vulnerability policy.
4. CI action pins.
5. Reproducible GoBGP v3.37, FRR 10.7.0, and BIRD 3.3.2 interop peers.
6. EN/RU security, dependency, changelog, and RFC-claim corrections.

No GoBGP v4 import, public API change, BFD feature, or broad refactor belongs in
this release.

The retained `e2e-core-testcontainers` compatibility target extends the single
Go-owned topology rather than creating a second lifecycle. Its bounded Go 1.27
image contains both `gobfd` and `gobfdctl`; a separately owned bounded tshark
image captures from `gobfd-a`'s immutable network namespace and decodes the
capture from the same content-addressed image without host mounts. The gate
asserts CLI list/show/monitor, host-mapped metrics, copied-config SIGHUP reload,
session continuity, bounded logs, explicit-timeout graceful stop, and Up plus
AdminDown packets. It writes the established `reports/e2e/core/<UTC run>/`
schema before LIFO cleanup and proves exact removal of four containers, one
network, and both images. The three established stderr artifacts are created
empty and mode `0600` before the first fallible evidence operation; command
failures overwrite their matching file with stderr truncated to the bounded
diagnostic limit while preserving the wrapped operation error. After live
parity and two independent reviews passed, `make e2e-core` was switched to this
Go runner and PR-safe CI was switched to invoke it exactly once. The retained
`e2e-core-testcontainers` target names the same underlying gate. The redundant
legacy files `run.sh`, `compose.yml`, `core_test.go`, and
`container_lookup_test.go`; Make targets `e2e-core-test`, `e2e-core-up`,
`e2e-core-down`, and `e2e-core-logs`; and the `e2e_core` build-tag profile were
then retired.

The BGP fast-failover compatibility target follows the same Go-owned lifecycle
boundary without retiring the operational example. The Go 1.27 testcontainers
gate uses the pinned GoBGP v3.37.0 and FRR 10.7.0 images on static
`172.22.0.0/24` addressing, rejects error-bearing readiness observations,
asserts exact `10.20.0.0/24` presence, BFD-driven withdrawal, and Established
plus route restoration, and records packet/container evidence before LIFO
cleanup. A live artifact-bearing gate and independent reviews proved all
recorded containers, network, image tags, and content IDs absent afterward.
`make int-bgp-failover` therefore names this authoritative Go gate, while the
deployment `run.sh`, Compose file, configs, and manual `-up`, `-logs`, and
`-down` targets remain available for operators.

The HAProxy health compatibility target is a separate pre-live Go 1.27
testcontainers/Podman gate; `make int-haproxy` remains the operational runner
until a later reviewed switch. It consumes the existing operational configs
without changing or mounting them, copies a test-only HAProxy config derived
in memory with a mapped local stats listener whose base URI is `/stats` while
the Go client requests `/stats;csv`, and keeps the immutable
HAProxy 3.4.3 and nginx 1.31.4 image pins. One bounded test-owned image, built
with the repository's exact Go 1.27 builder digest, contains `gobfd`,
`gobfdctl`, and `gobfd-haproxy-agent`; a separately owned bounded tshark image
provides capture and decoding. Both unique tags are rejected if they pre-exist,
their content IDs are recorded, and cleanup removes only exact test-owned
resources.

The topology uses static `172.23.0.0/24` IPAM: monitor plus agent at `.10`,
HAProxy at `.20`, nginx1 plus `backend1-bfd` at `.30`, and nginx2 plus
`backend2-bfd` at `.40`; capture shares the monitor namespace. Every shared
namespace is `container:<immutable-ID>`, all configuration and identity files
use testcontainers copy/reader support, and no host mount is permitted. The
monitor publishes agent ports 9990 and 9991 to random host ports for direct Go
TCP assertions. BFD state is queried only by executing the built `gobfdctl`
through the exact monitor container ID and decoding its existing JSON schema
strictly. HAProxy eligibility is queried through the mapped stats endpoint and
parsed fail-closed from the exact `http_back/srv1` and `http_back/srv2` rows.

Initial acceptance requires both BFD sessions Up, both agent responses
`up ready`, both HAProxy servers eligible, and both unique backend identities
served. The deterministic failure mutation pauses the immutable exact
`backend1-bfd` sidecar ID, never nginx `backend1`: only peer `.30` and agent
port 9990 become Down, srv1 becomes ineligible, srv2 remains healthy, direct
mapped access proves nginx1 is still reachable, and HAProxy serves only
backend2. Unpausing the same sidecar ID must restore the complete initial
state. All readiness and state transitions use context-bounded polling that
rejects error-bearing observations. Before LIFO resource cleanup the gate
writes bounded environment, ownership, container snapshot/log, pcapng,
decoded CSV, diagnostics, and summary evidence under
`reports/e2e/haproxy-health/<UTC run>/`; Make supplies the go-test JSON/log.
Final exact endpoint checks prove absence of every recorded container name and
ID, network, image tag, and owned content ID. The operational Compose,
`run.sh`, configs, and `int-haproxy-up`, `int-haproxy-down`, and
`int-haproxy-logs` targets remain unchanged.

The observability compatibility target is likewise a separate pre-live Go
1.27 testcontainers/Podman gate. The operational `make int-observability`
runner, Compose file, configs, and `-up`, `-down`, and `-logs` targets remain
unchanged. The Go gate copies the operational GoBFD, FRR, Prometheus rule and
scrape, and Grafana dashboard/provisioning assets without host mounts; only
the Grafana datasource URL is minimally derived for the test's static
Prometheus address. It retains the immutable FRR 10.7.0, Prometheus 3.14.0,
and Grafana 13.2.0 pins, and builds bounded test-owned GoBFD and tshark images
with the repository's exact Go 1.27 builder. The sole permitted runtime mount
is the official Prometheus image's one RW anonymous `volume` at
`/prometheus`; its nonempty generated name is inspected and written to
`resources.json` by a pre-start hook before readiness begins.

The topology uses static `172.25.0.0/24` IPAM with GoBFD at `.10`, FRR at
`.20`, Prometheus at `.30`, and Grafana at `.40`; capture shares the immutable
GoBFD container namespace. Initial acceptance proves the BFD session Up,
Prometheus's exact GoBFD target Up with the expected
`gobfd_bfd_sessions` series, Grafana database health/version, and the
authenticated provisioned Prometheus datasource and GoBFD dashboard. Pausing
the immutable exact FRR ID must produce BFD Down while the GoBFD scrape target
remains Up and `BFDSessionDownTransition` becomes firing. Session registration
also publishes the alert-critical `Up` to `Down` transition counter at zero.
Because the session gauge and transition vector are separate collectors,
initial acceptance independently queries Prometheus for that exact
peer/local/`Up`/`Down` series and requires a stored value of zero before the
FRR pause, closing scrape interleavings for the unchanged `increase(...[1m])`
rule. Unpausing that same ID must restore BFD Up, retain target health, and
context-bounded polling must observe the rule become inactive after its full
range window plus evaluation cadence.

The compatibility recipe reserves an exclusive absolute mode-0700 report
directory in the observability report parent, binds it to the Go test with an
explicit ownership marker, and snapshots both `go test` and `tee` pipeline
statuses before checking that both output artifacts are nonempty. Before LIFO
cleanup the gate writes bounded pcapng/decoded packet, container inspect/log,
Prometheus/Grafana/BFD JSON, environment, diagnostics, an atomically replaced
mode-0600 ownership ledger, and an explicitly pending summary. Only the final
summary cleanup writes a numeric result after cleanup and final
selected-endpoint checks prove every recorded test-owned container name and
immutable ID, network, image tag, content ID, and exact Prometheus volume name
absent; container termination's volume-removal request is not treated as proof.
`make int-observability-testcontainers` is only a compatibility target until a
later live run and independent review authorize any primary-target switch.

The pre-live SPEC gate additionally requires the runtime contract to inspect
the four network-namespace owners by immutable ID through the selected Podman
API endpoint and fail unless monitor, HAProxy, backend1, and backend2 report
exact IPv4 addresses `.10`, `.20`, `.30`, and `.40` on the created network.
The current bounded `podmanapi` helper has no network-inspect operation, so the
subnet and gateway remain enforced at the explicit network-create IPAM request;
they must also be asserted from runtime state if that helper later exposes
network inspection. Immediately after each successful image build, and before
provider close or any later fallible operation, the selected-endpoint client
inspects the exact unique tag, validates one lowercase 64-hex `sha256:` content
ID, and records it in the mutable ownership snapshot. Container evidence
rejects an empty or oversized individual inspect response and rejects an
oversized aggregate `containers.json`; it writes no truncated or partial JSON
as successful evidence and records every inspection, encoding, size, or write
failure in the pre-initialized bounded `containers.err` diagnostic.

The host-safe quality contract also bounds Podman API response reads at one
package limit, validates exec start/inspect HTTP status and strict exit-code
JSON, and propagates transport, status, and decode failures. Runtime-contract
failures return through topology startup so the initialized `containers.err`
records them. Go 1.27 session JSON rejects invalid UTF-8, duplicate object
members, unknown fields, and trailing values. Tshark stdout is bounded before
becoming CSV while bounded stderr and failure streams remain diagnostic-only.
Only the `resources.json` ownership ledger uses a rooted same-directory
mode-0600 temporary file followed by sync, close, and atomic rename.
`containers.json` remains bounded direct evidence written mode 0600 after
strict inspection, encoding, and size checks. The compatibility recipe runs
every tagged package test in one invocation under `umask 077`, requires a
nonempty go-test JSON artifact, and therefore creates the report directory as
0700 and the go-test JSON/log files as 0600.

The bounded live gate passed on 2026-08-24 with Go 1.27.0, Podman 5.8.2,
testcontainers-go 0.44.0, and HAProxy 3.4.3. The retained
`reports/e2e/haproxy-health/20260824T195549Z/` evidence contains 97 decoded BFD
packets across Down, Init, and Up, exact runtime addresses and immutable shared
network namespaces for all nine mountless containers, and HAProxy `srv1`
agent-check Down followed by restored Up while `srv2` remained healthy. The
gate then proved every recorded container ID and name, network, image tag, and
content ID absent; the one run-owned dangling builder was independently
identified and removed without a global prune.

## Machine-readable dependency evidence

The schema-v2 inventory records the complete external selected build lists
(192 runtime modules and 387 isolated tool modules), plus every declared
non-Go component. Assessments are embedded in each record; shared profiles may
not broadcast one license or repository conclusion across unrelated records.
Each record has canonical source, package-URL, commit, or digest coordinates
and keeps these independent review dimensions:

- repository archived state;
- artifact availability;
- release-line end-of-life state.

A `verified` or `stale` review cites a structured evidence ID whose subject and
review field exactly match that record. Evidence includes the source,
command/query, tool and version, observation time, result, and result hash.
The offline checker rejects duplicate or dangling evidence, stale source
locations, incomplete selected graphs, and immutable claims based only on a
tag.

The per-record provenance pass resolves 614 selected Go module records through
the stable deps.dev v3 exact-version endpoint or exact-commit GitHub license
files. `chzyer/logex` is explicitly not applicable because it contributes no
package to the distributed tool closure. Generation uses four bounded API
workers and fails closed on transport, HTTP, size, JSON-stream, or returned
identity errors; the committed checker remains offline.

Immutable OCI records bind their digest to reviewed source and license
evidence. Canonical records use an image build-source repository, exact source
commit, SPDX or precise LicenseRef, and the SHA-256 of the license file at that
commit. Registry manifest availability is separate evidence and never implies
source, repository activity, or license. Labels, when present, are
source-discovery hints only.

Alpine Linux is prohibited throughout first-party build, runtime, benchmark,
smoke, interop, and integration images. OS baselines are restricted to Debian
trixie or Oracle Linux 10, selected explicitly by use case and pinned to an
immutable multi-platform OCI index. The former Alpine benchmark, debug,
containerlab, RFC reflector, smoke, HAProxy, and NGINX paths use Debian trixie;
the obsolete Alpine package-corpus evidence is removed rather than retained as
historical authority. Seven mutable vendor/local images remain explicit
deferred decisions. Declared non-Go tools and the locked Python corpus are
separately bounded by `gobfd-qj0.8.1.12`.

GitHub Action repository, archive, and license metadata remain recorded per
repository. The archived `ovn-org/libovsdb` repository and the retained, ended
GoBGP v3 release line remain explicit record-level facts. The active libovsdb
successor migration is tracked by `gobfd-qj0.8.1.14` rather than hidden as a
mechanical version update.
