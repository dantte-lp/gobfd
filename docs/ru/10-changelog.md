# Changelog и выпуск релизов

Изменения для пользователей записываются в [CHANGELOG.md](../../CHANGELOG.md)
и [CHANGELOG.ru.md](../../CHANGELOG.ru.md). Содержание обеих версий должно
совпадать по смыслу. Это руководство описывает процесс и не дублирует
меняющиеся записи `Unreleased`.

## Формат changelog

Следуйте [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) и
[Semantic Versioning](https://semver.org/spec/v2.0.0.html).
Сначала размещается `Unreleased`, затем датированные версии от новых к старым.
Даты имеют формат `YYYY-MM-DD`; заголовки версий ссылаются на неизменяемые
теги или сравнения. Опубликованная история сохраняется. Добавляются только
непустые разделы `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security`.

Записывайте изменения поведения, видимого пользователям: конфигурации,
значений по умолчанию, протокольных процедур, API, CLI, метрик, безопасности
и совместимости. Внутренний рефакторинг, изменения тестов и исправления
опечаток сами по себе не требуют release entries. Описывайте результат и его
ограничения. Не вставляйте журнал commit и не заявляйте ускорение без измерений.

```markdown
## [Unreleased]

### Fixed
- Неподдерживаемые изменения аутентификации отклоняются до принятия поколения reload.
```

Указывайте фактическое поведение и границы приёмки. Пример оформления не
является заявлением о реализации другой процедуры RFC.

## Владение ветками

| Ветка | Назначение |
|---|---|
| `dev` | Интеграция следующей продуктовой линии; стабильные теги на ней не создаются |
| `master` | Ветка по умолчанию с последним принятым стабильным состоянием |
| `release/vMAJOR.MINOR` | Поддерживаемая продуктовая линия после review и квалификации |
| `fix/vMAJOR.MINOR-*` | Maintenance-исправление для соответствующей поддерживаемой линии |

`release/v0.6` сохраняет GoBGP v3.37.0 и контракты v0.6. Приёмка изменения
в `dev` не означает его доставку в эту линию или в `master`.

После публикации maintenance patch доставьте принятую стабильную историю
и оба changelog в `master` до закрытия релиза. Применимые изменения отдельно
переносятся в `dev`. Существующие теги не переписываются; неудачные версии
не используются повторно.

## Процесс выпуска

Подготовка релиза начинается после завершения реализации и финальной
квалификации. Исполняемый план и условия одобрения хранятся в Beads.
Текущая проверка документации перед публикацией — `gobfd-qj0.8.2.8.7.2.3`.

До создания release branch или тега проверьте активность соответствующих
rulesets для веток и тегов. Тег указывает на точный проверенный commit
release branch. Существующие теги неизменяемы, включая неудачные и
неопубликованные версии. Выбирайте новую свободную версию; не копируйте
старый пример создания тега.

Обновите оба changelog для фактического кандидата, перенесите принятые записи
`Unreleased` в датированный раздел и обновите ссылки сравнения. Выполните
необходимые локальные и release-проверки этого commit. Внешние записи требуют
действующего разрешения на публикацию; эта инструкция не снимает запрет доставки.

Workflow [release.yml](../../.github/workflows/release.yml) использует Go-owned
шаги `cictl` для preflight, notes, проверки и публикации:

1. Отклонить кандидата, если для него уже существуют release, draft или
   версионированные OCI-теги.
2. Извлечь все maintenance-разделы после предыдущего опубликованного
   стабильного релиза той же линии; для первого выпуска линии используется
   предыдущий стабильный релиз среди линий. Привязать notes и сравнения к тегу.
3. Собрать бинарники, DEB/RPM и Debian trixie OCI-продукты. Oracle Linux 10
   исключён из v1 OCI и lifecycle qualification; создание общего RPM сохранено.
4. Приложить все обязательные assets к draft и проверить checksums, notes,
   commit, SBOM/provenance, пакеты, OCI evidence и release report.
5. Опубликовать только полный проверенный draft. Независимый postpublication
   readback и закрытие поддерживаемых веток — отдельные шаги maintainer;
   `release-publish` является terminal mutation workflow.

Наличие workflow не доказывает прохождение этих шагов текущим кандидатом.
Не запускайте команды публикации для проверки документации.

## Экспериментальные prereleases

SemVer допускает суффикс вроде `v1.0.0-alpha.1`. Текущие
`cictl release-preflight` и `release-notes` принимают только канонические
**стабильные** теги. Пути доставки alpha в них нет.
[ADR-0008](adr/0008-experimental-prerelease-boundary.md) остаётся предложением;
Beads `gobfd-qj0.8.2.6.4` содержит отдельную квалификацию экспериментального канала.
Alpha не должен продвигать stable aliases или подменять стабильную приёмку.
