## Протокол и варианты исполнения — 2026-08-19

- Единый подключённый сокет TX отклонён: он не сохраняет стабильный исходящий порт на сессию и рекомендуемую уникальность по RFC 5881. Пул сокетов, обоснованный измерениями, обязан сохранять привязку сессии к порту.
- Фильтр TTL на UDP-сокете на основе классического BPF (cBPF) с фиксированными смещениями отклонён как небезопасное решение для IPv4/IPv6. Проверка TTL/Hop Limit из сопутствующих данных остаётся определяющей до замены полным решением TC/XDP, интегрированным с владельцем.
- `SO_REUSEPORT` требует привязки дискриминатора и peer к рабочему процессу и политики начальных пакетов при `YourDiscriminator=0`. Шардирование, колёса таймеров, реестры с копированием при записи, пакетный приём и io_uring требуют доказательств профилирования; архитектура FRR/BIRD сама не обосновывает их для Go.
- Программные метки времени приёма ядра требуют явного преобразования между шкалами реального времени ядра, аппаратных часов точного времени (PHC) и монотонного времени Go. Обнаружение отказа основано на монотонном времени принятого пакета до доказательства эквивалентного поведения при поздней доставке.
- systemd FDSTORE сохраняет дескрипторы, а не конечный автомат BFD (FSM), аутентификацию, состояние Poll, предельные сроки или владение актуатором. Тёплый перезапуск требует отдельного решения о переносе состояния; перезапуск без переключений состояния не обещается.
- Отражатель и инициатор S-BFD отложены за пределы v1 и требуют корректных Poll/Final, владения дискриминатором, списков контроля доступа, ограничений частоты и перестановки портов UDP/7784.
- Экспериментальные RFC 9985/9986 требуют полного механизма Poll, классификации значимых изменений, правил аутентификации More/Less Computationally Intensive (MCI/LCI) и периодической повторной аутентификации MCI. В стабильный v1 не входят.
- AF_XDP и перенос FSM в ядро вводят ещё одного владельца состояния и остаются исследованием после v1. Независимое подключение TC/XDP может конфликтовать с очисткой и резервным путём Cilium; будущий путь требует версионируемого контракта хука или плагина, принадлежащего Cilium.
- Все четыре поставляемых исполняемых файла сохраняются намеренно. Удаление неиспользуемых путей требует доказательств покрытия и использования; спекулятивное разделение модулей отклонено. Корректность состояния, переподключения и значений по умолчанию сопутствующих программ предшествует заявлениям о стабильности.

Подробные требования к Poll, диагностике, AdminDown, типизированной доставке, владению, защищённому управлению, QoS и масштабу сохранены в контракте продукта без дублирования исторических открытых задач.

## Peer Holo и жизненный цикл — 2026-08-20

Четвёртым peer выбран внешний Holo v0.9.0 с официальным идентификатором образа amd64:

```text
ghcr.io/holo-routing/holo-bundle@sha256:5c1f61475b1623b3eab611921f8319fb0a10492ced3f7da05e656418abb5ca4a
```

Датированный источник фиксирует лицензию MIT, поддержку RFC 5880/5881/5882/5883, проверку RFC 5880 §6.8.6 и аттестацию происхождения in-toto. Тогда базовая проверка уже использовала amd64; отсутствие многоархитектурного манифеста не сужало область. Зафиксированная квалификация на работающей системе достигла локального и удалённого Up при TX 300 ms и обнаружении отказа 900 ms; остановка Holo дала Down/`ControlTimeExpired` после этого интервала. Эти наблюдения не квалифицируют более поздний образ или топологию.

Замена сохраняет четыре независимые реализации: FRR, BIRD3, Holo и Thoro/bfd. Прежний peer и его средства измерений на Python удаляются из эксплуатационных потребителей; опубликованная история changelog сохраняется. Оставшаяся схема межъязыковых измерений содержит Go, C в стиле FRR и C в стиле BIRD без утверждений, выведенных из удалённых входных данных. Генератор недопустимых векторов использует кодеки Go с сохранением прежнего идентификатора сервиса `scapy`. ExaBGP остаётся внешним peer на Python; решение не добавляет исходники Rust, метаданные Cargo, инструментарий, локально собираемую обёртку Holo или дополнительную зависимость Python.

Историческая закрытая лаборатория использует Holo `172.20.0.50` и GoBFD `172.20.0.10`: это зафиксированные лабораторные адреса, а не рекомендуемые публичные примеры. Holo использует `NET_RAW`/`NET_ADMIN`, пользователя `holo` и путь базы данных образа, конфигурацию демона TOML только для чтения, северный интерфейс gRPC и логирование в stdout; запись логов в файл и неиспользуемый gNMI выключены. Отдельный файл команд YANG, доступный только для чтения, задаёт `eth0`, `ietf-bfd-types:bfdv1`, множитель 3 и TX/RX `300000` микросекунд. `holod -c` принимает TOML, а не YANG. Одноразовый загрузчик с тем же digest ждёт исправного состояния gRPC демона и применяет YANG через `holo-cli`; успешное завершение обязательно для readiness. Загрузчик не имеет статического адреса и не является ещё одним peer.

Приёмка жизненного цикла фиксирует границу кадра и метки времени захвата до остановки или перезапуска. Восстановление требует нового пакета Holo Up после этой границы и текущих локального и удалённого Up в API GoBFD; отказ требует текущего локального Down/`ControlTimeExpired`. Старого пакета Up недостаточно. Наборы тестов с тегами требуют ненулевого числа входных тестов и проверок установления соединения, независимых сессий, отказа и восстановления, дискриминатора и RFC 5880/5881. Обязательные обычные проверки гонок, vet, модулей, строгий lint и проверки документации остаются независимыми.

Диагностика отказов сохраняет логи демона и загрузчика, а также резервный `/tmp/holod.err`. Предварительная проверка определяет точный проект Compose и запрещает продолжение при существовании любого контейнера, сети или тома с его меткой. Очистка затрагивает только записанные ресурсы с метками проекта, после частичного отказа определяет точные ID оставшихся ресурсов и проверяет их отсутствие как при успехе, так и при ошибке. Загруженные и собранные образы — общие входные данные кеша, без неявного владения в рамках прогона; они сохраняются. Явно выделенные уникальные образы аудита имеют отдельное владение. Посторонние ресурсы не затрагиваются.

Отклонены сокращение матрицы до трёх, незрелые peer без стабильного выпуска, обёртки демона в репозитории и предположения, привязанные к платформе; peer с передачей данных в ядре остаются необязательным исследованием. Предложения интеграции Cilium/Calico и делегирование MetalLB в FRR не дают ещё одной независимой реализации BFD.

Источники: [Holo v0.9.0](https://github.com/holo-routing/holo/releases/tag/v0.9.0), [исходники BFD на теге](https://github.com/holo-routing/holo/tree/v0.9.0/holo-bfd), [TOML демона](https://github.com/holo-routing/holo/blob/v0.9.0/holo-daemon/holod.toml), [RFC 9314 YANG](https://www.rfc-editor.org/rfc/rfc9314.html).

Доступность реестра не доказывает исходник, активность или лицензию; метки служат только подсказками поиска. Исходные узкие заметки v0.6.4 пропустили неопубликованные изменения сопровождения v0.6.2/v0.6.3; changelog `master` отставали на v0.6.2. PR #67/#68 исправили накопительные заметки и синхронизировали все три ветки без изменения неизменяемого тега и артефактов. Приёмка публикации отделена от последующих пробелов применимости к стабильной линии и квалификации.

Повторно используемая политика публикации завершает артефакты в черновике до публикации: точная проверка аннотированного тега и вершины ветки, непустые накопительные заметки changelog, проверки содержимого контрольных сумм, SBOM, происхождения, пакетов и OCI, один исполняемый дескриптор на платформу, разбор фактических данных SPDX и SLSA v1, затем продвижение псевдонимов с проверкой digest и окончательная публикация. Дублирующиеся черновики, артефакты и версионированные ссылки OCI запрещают продолжение; незаметная замена и `--clobber` запрещены. Неудачный выпуск исправляется последующим изменением. Обязательные проверки Buf используют фактическую целевую ветку PR; наборы правил защищают ветки выпуска и неизменяемые теги до их создания. Актуальная процедура находится в регламенте выпуска.

## Решение eBPF — 2026-10-15

Оценка отклоняет интеграцию cilium/ebpf в v1. Зафиксированы v0.22.0, MIT, активный неархивный репозиторий, минимальная версия модуля Go 1.25.0, Linux amd64/arm64, отсутствие 32-битной поддержки и изменения API до 1.0; это датированные наблюдения, а не текущие рекомендации. В ревью выпусков v0.19.0–v0.22.0 не найдено опубликованного advisory безопасности; v0.21.0/v0.22.0 нарушали совместимость API, Linux 7.1 BTF требовал v0.22.0. README для части требований прочитан из `main`, а не из выпуска на теге. Совместимость Pure-Go/CGO выведена из исходников, сборка не выполнялась.

На дату оценки в репозитории не было зафиксировано исходных измерений сквозной задержки приёма или нагрузки системных вызовов; дополнительные привилегии и усложнение сборки не были обоснованы. `bpf2go` добавляет clang/LLVM, libbpf и заголовки ядра; Go `asm` не требует компиляции C, но сложнее для ревью. Загрузка требует `CAP_BPF` (или прежнего `CAP_SYS_ADMIN`), `bpf()` и разрешения семейства адресов AF_XDP, где оно применимо. Токены BPF требуют делегирования в runtime. Прототипы generic/driver на выделенном интерфейсе следуют за измеренным ограничением системных вызовов, не устранимым пакетной обработкой, и явным контрактом владельца плоскости данных.

Отражение Echo в ядре отклонено: RFC 9747 §2 использует обычную удалённую пересылку; лабораторный отражатель — средство тестирования. Потери на сокет учитываются через `SO_RXQ_OVFL` без eBPF. Фильтрация сокетов сама не обосновывает добавление библиотеки; проверка GTSM по сопутствующим данным уже существует. Полный FSM в ядре вне v1. Поведение `IP_MINTTL` для UDP не проверено и не принято этой записью.

Источники оригинала: [cilium/ebpf v0.22.0](https://github.com/cilium/ebpf/tree/v0.22.0), [socket(7)](https://man7.org/linux/man-pages/man7/socket.7.html), [capabilities(7)](https://man7.org/linux/man-pages/man7/capabilities.7.html), [RFC 9747 §2](https://www.rfc-editor.org/rfc/rfc9747.html#section-2).

## Транспорт управления — 2026-10-15

[Публичная задача #87](https://github.com/dantte-lp/gobfd/issues/87) фиксирует выбор Unix-сокета с UID peer от ядра для локальных клиентов и аутентифицированного TLS для удалённого TCP. Анонимный loopback не идентифицирует пользователя хоста или pod в сети хоста. Bearer token отклонён как более слабая общая идентичность с дополнительной обработкой секретов; обязательный локальный mTLS отклонён из-за эксплуатационных затрат; активация сокетов systemd отложена.

Принят `/run/gobfd/gobfd.sock`, режим 0660, владелец `gobfd`, группа `gobfd-admin`. Группа демона также читает конфигурацию секретов `root:gobfd` с режимом 0750 и не может служить группой администраторов-операторов. Пакет использует административную группу sysusers, дополнительное членство демона в группе и `RuntimeDirectory=gobfd`; настраиваемые путь, режим и группа позволяют общий контейнерный `emptyDir`. Субъект доступа — UID peer в пользовательском пространстве имён демона, никогда PID. Учётные данные извлекаются до обёрток, способных скрыть Unix-соединение. Устаревший путь удаляется лишь если это сокет без отвечающего сервера; обслуживание начинается после создания с ограниченными правами и chmod.

Пустой `grpc.addr` отключает необязательный TCP. Чтение через loopback совместимо; анонимное изменение требует явного `grpc.unsafe_loopback_mutations`, видимости при запуске и состояния управления `NOT_SERVING`. Незашифрованный доступ вне loopback отклоняется до начала обслуживания. TLS требует сертификат, ключ, клиентский CA, ALPN HTTP/1.1 и HTTP/2 и перечитывание файлов при рукопожатии через `GetConfigForClient`. Историческое наблюдение пакетного обмена показало ошибку grpc-go без `h2`: `tls: no application protocol`; listener использует собственный `tls.Config`, а не `ServeTLS`. Проверки протоколов Unix/TLS и реального пакетного обмена независимы; h2c и TLS используют разные listener.

Клиенты принимают `unix:///path`, `http://host:port`, `https://host:port`, флаги CA, сертификата и ключа TLS либо соответствующую конфигурацию; запись `host:port` без схемы означает HTTP. URI SAN mTLS (SPIFFE), иначе первый DNS SAN, определяет идентичность с явными ролями; заявки разных субъектов изолированы. Kubernetes использует совместное владение сокетом и exec-пробу состояния при выключенном TCP. Для существующих настроенных listener сохраняются указания миграции. Браузеры через Unix-сокеты вне области. Перечитывание сертификата не означает проверку отзыва; короткоживущее обновление и необязательные CRL/OCSP отделены. Текущее поведение и исправленную изоляцию транспортных субъектов определяет справочник безопасности.
