### Обзор

`gobfdctl` взаимодействует с демоном gobfd через ConnectRPC (совместим с протоколами gRPC, Connect и gRPC-Web). Поддерживает как неинтерактивные команды (через Cobra), так и интерактивную оболочку (через reeflective/console) с автодополнением по Tab.

```text
gobfdctl [глобальные флаги] <команда> [подкоманда] [флаги]
```

### Глобальные флаги

| Флаг | По умолчанию | Описание |
|---|---|---|
| `--addr` | `unix:///run/gobfd/gobfd.sock` | Конечная точка демона gobfd: `host:port`, `http://host:port`, `https://host:port` или `unix:///path` (сокет управления) |
| `--tls-ca` | `""` | Файл CA, подписавшего сертификат демона (конечные точки `https://`) |
| `--tls-cert` | `""` | Файл сертификата клиента для mTLS |
| `--tls-key` | `""` | Файл ключа клиента для mTLS |
| `--format` | `table` | Формат вывода: `table`, `json`, `yaml` |

### Команда capabilities

```bash
gobfdctl capabilities
gobfdctl capabilities --format json
gobfdctl capabilities --format yaml
```

Вызывает RPC только для чтения `bfd.v1.CapabilityService.ListCapabilities`. Демон
возвращает пять профилей в порядке `unsolicited`, `echo`, `micro_bfd`, `vxlan`,
`geneve`. Колонки таблицы: `CAPABILITY`, `RFC`, `MATURITY`, `ENABLEMENT`,
`READINESS`; JSON и YAML возвращают массив объектов с полями `kind`, `rfc`,
`maturity`, `enablement`, `readiness`.

| Поле | Значения и смысл |
|---|---|
| `maturity` | `preview`; готовность среды исполнения не подтверждает квалификацию RFC |
| `enablement` | `disabled`, `enabled` либо `unknown`, когда состояние среды исполнения недоступно |
| `readiness` | `not_ready`, `ready` либо `unknown`, когда состояние среды исполнения недоступно |

Выключенные профили имеют `not_ready`. При отсутствии источника состояния среды исполнения
все пять предварительных профилей сохраняются со значением `unknown` в полях enablement
и readiness. CLI отображает незаданные значения enum как `unknown`; ошибка RPC возвращается без подстановки
локального каталога или определения статуса по клиентским флагам.

`ready` отражает необходимый принадлежащий владельцу путь приёма/backend и локальную
готовность среды исполнения, источника и привязок. Значение не доказывает исправность пиров,
соответствие RFC или действие актуатора L2. Развёртывание Echo только через API может
возвращать `not_ready`, пока последующий `echo add` не получит приёмный слушатель.
RPC статуса остаётся доступным при неготовой среде пересылки в рамках
политики транспорта управления и не передаёт адреса пиров, конечные точки или секреты.

### Команды сессий

#### Список всех сессий

```bash
gobfdctl session list
```

Таблица показывает идентичность по адресам пира и локальной системы, текущее состояние,
тип и дискриминаторы. Поля таймеров доступны в `session show` или структурированном выводе JSON/YAML.

#### Показать конкретную сессию

```bash
# По адресу пира
gobfdctl session show 10.0.0.1

# По локальному дискриминатору
gobfdctl session show 42
```

Если адресу пира соответствует несколько сессий (например, один пир на двух
интерфейсах), запрос завершается с `FAILED_PRECONDITION` и перечисляет
локальные дискриминаторы; сессию нужно запросить по дискриминатору.

#### Создать сессию

```bash
# Single-hop BFD-сессия
gobfdctl session add \
  --peer 10.0.0.1 \
  --local 10.0.0.2 \
  --interface eth0 \
  --type single-hop \
  --tx-interval 100ms \
  --rx-interval 100ms \
  --detect-mult 3

# Multihop-сессия
gobfdctl session add \
  --peer 192.168.1.1 \
  --local 192.168.2.1 \
  --type multi-hop \
  --tx-interval 300ms \
  --detect-mult 5

# Аутентифицированная сессия
gobfdctl session add \
  --peer 10.0.0.1 \
  --local 10.0.0.2 \
  --auth-type keyed-sha1 \
  --auth-key-id 7 \
  --auth-secret api-auth-secret \
  --padded-pdu-size 128
```

| Флаг | Обязательный | По умолчанию | Описание |
|---|---|---|---|
| `--peer` | Да | -- | IP-адрес удалённой системы |
| `--local` | Нет | -- | Локальный IP; задайте явно для квалификации привязки приёма |
| `--interface` | Нет | -- | Привязка одношагового RX/TX к устройству; для `multi-hop` запрещён |
| `--type` | Нет | `single-hop` | Тип сессии: `single-hop` или `multi-hop` |
| `--tx-interval` | Нет | `1s` | Desired Min TX Interval |
| `--rx-interval` | Нет | `1s` | Required Min RX Interval |
| `--detect-mult` | Нет | `3` | Множитель обнаружения |
| `--padded-pdu-size` | Нет | `0` | Целевой размер PDU в байтах: 0 отключает дополнение; 24-9000 без аутентификации, 26-9000 с ней |
| `--auth-type` | Нет | `none` | Тип аутентификации: `none`, `simple-password`, `keyed-md5`, `meticulous-keyed-md5`, `keyed-sha1`, `meticulous-keyed-sha1` |
| `--auth-key-id` | Нет | `0` | Auth Key ID RFC 5880, диапазон 0-255; ноль допустим |
| `--auth-secret` | Если аутентификация включена | -- | Секрет: 1-16 байт для Simple Password/MD5, 1-20 байт для SHA1 |

`AddSession` возвращает `InvalidArgument` при некорректной структуре protobuf
длительностей TX/RX и при отклонении клиентских интервалов проверками ядра.
Пропущенные интервалы получают `1s`; явно заданный требуемый интервал RX, равный нулю,
остаётся допустимым.

`session show` отображает `Padded PDU Target` в байтах. JSON/YAML вывод сессий,
включая строки monitor, передаёт настроенный целевой размер целым `padded_pdu_size`;
аутентифицированный PDU может быть длиннее. CLI/API `0` отключает дополнение, а `0`
в YAML-сессии наследует `bfd.default_padded_pdu_size`.

#### Удалить сессию

```bash
gobfdctl session delete 42
```

### Команды echo

Сессии независимого BFD Echo по RFC 9747 выделены в отдельную группу
команд: их таймерная модель отличается от контрольных сессий RFC 5880 —
TxInterval задаётся локально и не согласуется с пиром.

`echo add` требует `echo.enabled: true` у демона и готового пути приёма Echo.
Выключенный предварительный режим, ожидающее или неуспешное согласование,
потеря готовности среды исполнения или привязки возвращают `FailedPrecondition`
без открытия отправителя и создания сессии. List/Delete остаются доступны
для очистки. RFC 9747 остаётся предварительной реализацией.

#### Список echo-сессий

```bash
gobfdctl echo list
```

#### Создать echo-сессию

```bash
gobfdctl echo add \
    --peer 10.0.0.1 \
    --local 10.0.0.2 \
    --tx-interval 50ms \
    --detect-mult 3
```

| Флаг | Обязательный | По умолчанию | Описание |
|---|---|---|---|
| `--peer` | Да | -- | IP-адрес цели Echo |
| `--local` | Нет | -- | Локальный IP; задайте явно для проверки привязки приёма |
| `--interface` | Нет | -- | Опциональная привязка приёмного слушателя и отправителя Echo через `SO_BINDTODEVICE` |
| `--tx-interval` | Нет | `1s` | Локально настроенный интервал отправки Echo (RFC 9747 Section 2) |
| `--detect-mult` | Нет | `3` | Множитель обнаружения; `DetectionTime = mult * TxInterval` |

`AddEchoSession` требует структурно корректный положительный `tx_interval`
в границах интервала BFD на проводе; нарушения возвращают `InvalidArgument`. CLI
передаёт своё значение по умолчанию `1s`, а прямой API-запрос должен содержать это поле.

Echo через API отправляет на UDP-порт назначения 3785 и получает приёмный
слушатель для запрошенных локального адреса и интерфейса. Ошибка создания
отправителя освобождает подготовленное право приёма и неиспользованный порт источника.
Echo остаётся предварительной реализацией; локальные проверки сокетов не
подтверждают совместимость с пирами или полную квалификацию RFC 9747.

Повторный допущенный одинаковый Echo Add того же принципала возвращает прежний
дискриминатор без открытия нового отправителя. Совместимые владельцы конфигурации и
другие принципалы API разделяют протокольную сессию; конфликт параметров возвращает
`FailedPrecondition`. Delete освобождает только право вызывающего
(`PermissionDenied` без него, `NotFound` при отсутствии дискриминатора). Только
освобождение последнего права завершает сессию; удаление конфигурации сохраняет RX/TX для
оставшегося владельца API.

#### Удалить echo-сессию

```bash
gobfdctl echo delete 42
```

### Команды micro-BFD

RFC 7130 micro-BFD использует одну BFD-сессию на каждую линию участника LAG.
CLI управляет ресурсом группы; создание сессий участников — отдельная операция.
Создание требует `micro_bfd.enabled: true` у демона; иначе возвращается
`FailedPrecondition`. В CLI нет команды создания сессий участников; используйте
декларативную конфигурацию группы для совместного создания группы и её участников.

#### Список micro-BFD групп

```bash
gobfdctl micro list
```

#### Создать micro-BFD группу

```bash
gobfdctl micro add \
    --lag bond0 \
    --members eth0,eth1,eth2 \
    --peer 10.0.0.1 \
    --local 10.0.0.2 \
    --tx-interval 300ms \
    --rx-interval 300ms \
    --detect-mult 3 \
    --min-active 2
```

| Флаг | Обязательный | По умолчанию | Описание |
|---|---|---|---|
| `--lag` | Да | -- | Имя LAG-интерфейса (`bond0`, `team0`, `port-channel1`) |
| `--members` | Да | -- | Имена линий участников через запятую |
| `--peer` | Да | -- | IP-адрес пира для всех сессий участников |
| `--local` | Нет | -- | Локальный IP-адрес |
| `--tx-interval` | Нет | `1s` | Желаемый минимальный интервал TX |
| `--rx-interval` | Нет | `1s` | Требуемый минимальный интервал RX |
| `--detect-mult` | Нет | `3` | Множитель обнаружения (RFC 7130 Section 2.2) |
| `--min-active` | Нет | `1` | Минимум активных участников для состояния Up агрегата |

CLI отклоняет `--min-active` вне диапазона `[1, len(--members)]` до
обращения к демону.

`AddMicroBFDGroup` возвращает `InvalidArgument` при некорректной структуре
длительностей protobuf TX/RX, повторяющихся или пустых именах участников и значениях
сессии участника вне границ RFC 5880 (нулевые или выходящие за диапазон интервалы,
нулевой множитель обнаружения). Пропущенные интервалы получают `1s`. RPC групп
Micro-BFD возвращают:

| Условие | Код |
|---|---|
| Вызывающий уже владеет правом на группу | `AlreadyExists` |
| Существует группа с тем же `lag_interface` и другой конфигурацией | `FailedPrecondition` |
| Линия участника принадлежит группе другого LAG | `FailedPrecondition` |
| `DeleteMicroBFDGroup` для группы, которой вызывающий не владеет, например группы перезагрузки конфигурации | `FailedPrecondition` |
| `DeleteMicroBFDGroup` для неизвестного LAG | `NotFound` |

#### Удалить micro-BFD группу

```bash
gobfdctl micro delete bond0
```

### Команда мониторинга

Стриминг BFD-событий (изменений состояния) в реальном времени:

```bash
# Только новые события
gobfdctl monitor

# События с начальным снимком всех сессий
gobfdctl monitor --current
```

| Флаг | По умолчанию | Описание |
|---|---|---|
| `--current` | `false` | Включить текущие состояния сессий перед стримингом |

Мониторинг использует поток ответов сервера. Таблица выводит время, тип
события, адрес пира, текущее и предыдущее состояние, локальный дискриминатор
и ревизию (`rev=`), возрастающую в пределах одного процесса демона. JSON/YAML
также передаёт диагностический код и причину из представления сессии CLI.
CLI выводит выбранные поля RPC: счётчики пакетов Control/Watch и
`ListSessions.delivery_counters` отсутствуют. Для этих счётчиков используйте
API или Prometheus. См. [`formatEvent`](../../cmd/gobfdctl/commands/format.go).

Снимок (`--current`) — последовательность событий `SessionAdded`, которую
закрывает `SyncComplete` с ревизией, покрытой снимком. Если мониторинг
отстаёт от демона, он получает `Gap` и затем новый снимок, с `--current` и
без него. Освобождение последнего владельца протокольной сессии создаёт
`SessionDeleted` с идентификаторами, последним состоянием и ревизией;
освобождение разделяемого права не создаёт событие удаления. Последующие снимки
не содержат удалённую сессию. Удаление отменяет её ожидающие действия
GoBGP Down и Up; ранее отключённый GoBFD пир не включается автоматически.

Новая Control- или Echo-сессия создаёт `SessionAdded`, даже оставаясь Down.
RPC добавления, изменения и удаления передают полный API-статус на границе публикации;
List измеряет телеметрию отдельно. `ObservationVersion` покрывает причинный
кортеж, а не каждый пакет или изменение счётчика. Клиент заменяет строку
целиком, включая нули, false и отсутствующие временные метки. Начальные снимки,
снимки GAP и переподключения включают оба реестра на одной границе ревизии.
Строки Echo передают локальный интервал TX, параметры обнаружения, счётчики и временные метки;
поля пира, согласования, потерь и аутентификации, которыми Echo не владеет,
равны нулю и не доказывают отсутствие потерь. Control List/Get и типизированные
команды Echo сохраняют прежнюю область. Потеря исходного публичного уведомления
Control/Echo также создаёт `Gap` и свежий снимок при работающем диспетчере, даже если
очередь самого монитора свободна. Следующий переход владельца или переподключение
не требуется. Общий клиент Watch отклоняет старые наблюдения из очереди после
нового снимка; CLI печатает поток событий с ревизиями. Частная очистка и
устаревшие подписчики сохраняют отдельные границы доставки.

Нажмите `Ctrl+C` для остановки.

CLI открывает один поток и завершается при его ошибке; автоматическое
переподключение отсутствует. Переподключение в общей клиентской библиотеке
не является гарантией команды monitor.

### Команда версии

Все бинарные файлы поддерживают отображение версии с хэшем коммита и датой сборки:

```bash
gobfd --version
gobfdctl version
gobfd-haproxy-agent --version
gobfd-exabgp-bridge --version
```

Пример вывода:

```text
gobfdctl v0.1.0
  commit:  abc1234
  built:   2026-02-22T12:00:00Z
```

Информация о версии внедряется при сборке через ldflags (см. [09-development.md](./09-development.md)).

### Обновление сертификата

Обновите существующий сертификат управления через явно доверенный внешний
Smallstep CA:

```bash
gobfdctl certificate renew \
  --ca-url https://ca.example \
  --ca-root /etc/gobfd/root.pem \
  --cert /etc/gobfd/management.pem \
  --key /etc/gobfd/management-key.pem
```

| Флаг | Обязателен | Описание |
|---|---|---|
| `--ca-url` | Да | HTTPS origin доверенного CA |
| `--ca-root` | Да | Явные PEM-корни для конечной точки CA и возвращённой цепочки |
| `--cert` | Да | Заменяемый PEM-файл существующего действующего сертификата |
| `--key` | Да | PEM-файл существующего соответствующего закрытого ключа |

Локальные флаги не имеют подстановки из окружения. Неинтерактивная команда
выполняет нативный mTLS-запрос `POST /renew` с HTTP-таймаутом 10 секунд и отменой
через контекст вызова, SIGINT или SIGTERM. Инициализация RPC демона обходится;
`--addr` и флаги управления `--tls-*` не задают доступ к CA.

Существующий сертификат должен быть пригоден для клиентской TLS-аутентификации
на CA. Если расширение EKU ограничивает назначения, оно должно разрешать
`clientAuth`; одного `serverAuth` недостаточно для аутентификации этого запроса.
Сертификату демона, используемому и для сервера управления, и для обновления,
нужны оба назначения. Обновление сохраняет профиль использования и не добавляет
недостающее назначение. См. [решение по транспорту Smallstep](adr/0005-smallstep-management-certificates.md).

Три входных файла должны быть разными обычными файлами с единственной жёсткой
ссылкой, без символической ссылки в последнем компоненте пути и с доверенными
родительскими каталогами. Файлы и их непосредственные родительские каталоги
недоступны для записи группе и остальным и принадлежат root или вызывающему
UID. Закрытый ключ имеет режим `0400` или `0600`. JSON-ответ сохраняет открытый ключ, subject, точный
SAN и профиль key usage/EKU; новый сертификат должен продлевать срок действия.
Идентичная проверенная цепочка не изменяет файл.

Атомарно заменяется только файл открытого сертификата с сохранением режима и
UID/GID; закрытый ключ не изменяется и не выводится. Успех выводит
`certificate renewed` или `certificate unchanged` независимо от `--format`.
Ошибки до замены сохраняют прежний сертификат. Ошибка `ErrCommitted` означает,
что замена уже произошла: долговечность записи может быть неопределённой,
откат не гарантируется. Этот признак сохраняется и при ошибке вывода после замены.

Первичный выпуск и автоматическое расписание не входят в команду. Доверенный
CA может выпускать идентификаторы, выбранные правилами ролей API; сам выпуск
не разрешает доступ к API. Ограниченная Linux-квалификация использует настоящую
CA с изолированным профилем зависимостей; см. [контракт теста](../../test/stepca/README.md).
Границы перечитывания сертификатов описаны в
[развёртывании](06-deployment.md#обновление-сертификатов-управления) и
[ADR-0005](adr/0005-smallstep-management-certificates.md).

### Интерактивная оболочка

```bash
gobfdctl shell
```

Запускает интерактивную оболочку с:
- **Автодополнением по Tab** для команд и подкоманд
- **Автодополнением readline** через reeflective/console (из дерева команд Cobra)
- Командами session, monitor, capabilities и version без префикса `gobfdctl`;
  обновление сертификата доступно только в неинтерактивном CLI

Пример сессии:

```text
gobfd> session list
gobfd> session show 10.0.0.1
gobfd> capabilities
gobfd> monitor --current
gobfd> exit
```

### Форматы вывода

Session list/show/add, echo list, micro list, monitor и capabilities поддерживают
три формата через `--format`. Echo/micro add и delete, session delete, version
и certificate renew выводят текст независимо от `--format`:

| Формат | Применение |
|---|---|
| `table` | Человекочитаемый вывод в терминал (по умолчанию) |
| `json` | Машиночитаемый, скриптинг, конвейер к `jq` |
| `yaml` | Структурированный человекочитаемый вывод |

Имена и значения полей JSON образуют машиночитаемый контракт CLI. YAML сохраняет
ту же модель данных, но пробелы, отступы и представление скаляров не являются
побайтово стабильными при совместимых обновлениях сериализатора; автоматизация
должна разбирать YAML, а не сравнивать его отрисованный текст.

Подробный статус Control-сессии показывает `Packets Dropped` и `Auth Failures` из тех же
измеренных счётчиков сессии, что Get/List и Control Watch. Ошибки аутентификации входят в
потери; принятый в очередь пакет может быть отклонён владельцем или оставлен без обработки
при остановке. Итоги стадий за срок жизни процесса, включая неизвестных пиров и удалённые
сессии, доступны через API `ListSessions.delivery_counters` и
`gobfd_bfd_delivery_outcomes_total`. Фиксированные строки также различают Echo
RX и исходы исходных уведомлений, диспетчеризации и доставки получателю; потеря уведомления
не является потерей пакета Control. Таблица сессий их не отображает. Знаменатели
и оставшиеся очереди описаны в [мониторинге](07-monitoring.md).

```bash
# JSON-вывод для скриптов
gobfdctl session list --format json

# YAML-вывод
gobfdctl session list --format yaml

# Конвейер JSON к jq
gobfdctl session list --format json | jq '.[].local_state'
```

### Примеры

```bash
# Подключение к удалённому демону
gobfdctl --addr https://gobfd.example.net:50052 \
  --tls-ca /etc/gobfd/ca.crt --tls-cert /etc/gobfd/client.crt \
  --tls-key /etc/gobfd/client.key session list

# Быстрая настройка сессии для тестирования
gobfdctl session add --peer 10.0.0.1 --local 10.0.0.2 --interface eth0 \
  --tx-interval 100ms --detect-mult 3

# Отслеживание изменений состояния в JSON
gobfdctl --format json monitor --current

# Проверка состояния в скрипте
if gobfdctl session show 10.0.0.1 --format json | jq -e '.local_state == "Up"' > /dev/null; then
  echo "BFD session is Up"
fi
```
