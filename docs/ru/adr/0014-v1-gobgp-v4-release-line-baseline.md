# ADR-0014: Перевод ветки release/v1.0 (GoBGP v4) к выпуску 1.0.0 и межмажорная база бенчмарков

[Английский оригинал](../../en/adr/0014-v1-gobgp-v4-release-line-baseline.md).

| Поле | Значение |
|:---|:---|
| Status | Принято |
| Date | 2026-11-27 |

## Контекст

Ветка `release/v0.6` (`v0.6.4`) сопровождает линию с зависимостью от GoBGP v3 (`v3.37.0`, `/apipb.GobgpApi`) и плоским ключом поиска сессий `(peer, local, interface)`. Ветка `release/v1.0` образует новую мажорную продуктовую линию с зависимостью от GoBGP v4 (`v4.11.0`, `/api.GoBgpService`), семипольным каноническим ключом `SessionKey` (`type`, `address_family`, `peer`, `local`, `interface`, `network_scope`, `transport_scope`), claims владения по субъектам доступа, защитой управления по умолчанию через Unix-сокет и учётом доставки и отбросов по поколениям.

Два ограничения автоматизации выпуска препятствовали прямому переводу `release/v1.0` к стабильному `v1.0.0`:

1. [release-please-config.json](../../../release-please-config.json) оставался закреплён в режиме `"versioning": "prerelease"` (`"prerelease": true`, `"prerelease-type": "alpha"`) согласно [ADR-0008](0008-experimental-prerelease-boundary.md), из-за чего автоматическое предложение версий формировало только `1.0.0-alpha.N`.
2. В [.github/workflows/release.yml](../../../.github/workflows/release.yml) команда `cictl release-benchmark-comparison` сравнивает новый тег с предыдущим опубликованным стабильным выпуском (`v0.6.4`) через [benchmark_report.go](../../../test/internal/cirunner/benchmark_report.go). Поскольку `v1.0` добавляет на приёмном пути проверку `transport_scope`, учёт доставки по поколениям владельца и типизированные счётчики перегрузки при сохранении `0 B/op` и `0 allocs/op`, `BenchmarkManagerDemux1000Sessions` составляет ~180 ns/op на `release/v1.0` против ~81 ns/op на `v0.6.4` (+124%). При едином пороге отказа `>= 10%` `critical` между разными мажорными версиями переход `v0.6.4 -> v1.0.0` завершается отказом уже после создания неизменяемого тега под действием набора правил `release-tags`.

2026-11-27 сопровождающий принял решение готовить `release/v1.0` непосредственно к выпуску `1.0.0` как новой мажорной ветки с зависимостью от GoBGP v4, сохранив границы зрелости preview/experimental-расширений в [матрице покрытия RFC](../08-rfc-compliance.md) и выведя многочасовые soak-кампании и стенды аппаратных NOS за пределы блокеров публикации `1.0.0`.

## Решение

### 1. Перевести `release/v1.0` на предложение стабильной версии `1.0.0`

Настроить [release-please-config.json](../../../release-please-config.json) в ветке `release/v1.0` на `"versioning": "default"` с сохранением `"skip-github-release": true` и `"skip-changelog": true`. Использовать однократный трейлер `Release-As: 1.0.0` при слиянии подготовительного изменения, чтобы Release Please обновил открытый PR выпуска для `release/v1.0` на версию `1.0.0` без жёсткой фиксации версии для последующих выпусков `1.0.x`. Сохранить [ADR-0008](0008-experimental-prerelease-boundary.md) и исторический тег `v1.0.0-alpha.1` (`206d25bccd4039dae746ddc8e85b16f277dd4588`) без изменений.

### 2. Установить границу межмажорного сравнения бенчмарков выпуска

Обновить [benchmark_report.go](../../../test/internal/cirunner/benchmark_report.go) (`applyCrossMajorReleasePolicy`), чтобы при сравнении канонических релизных тегов разных мажорных линий в `BenchmarkReleaseContext` (база `v0` против цели `v1`):

1. Полный набор из десяти чередующихся пар без race и предварительная проверка `-race` на приёмных бенчмарках выполнялись без изменений на `v0.6.4` и целевом commit `v1.0.0` с проверенным overlay `decode-packet-per-iteration-v1`.
2. Изменения `sec/op` уровня `critical` на архитектурной границе `v0 -> v1` переводились в категорию `"reported"` в `comparison-vs-baseline.json` с добавлением явной записи о смене мажорной базы в `comparison-vs-baseline-notes.txt`, формируя новую базу линии `v1` без аварийной остановки `release.yml`.
3. Проверки бенчмарков в pull request (`ReleaseContext == nil`), сравнения внутри одной мажорной линии (`v0.6.x -> v0.6.y` и `v1.0.0 -> v1.x.y`), а также неканонические идентификаторы базы сохраняли строгий отказ `critical` (`errCriticalBenchmarkRegression` при `>= 10%`).

### 3. Сохранить явные границы зрелости возможностей в `v1.0.0`

Выпуск `v1.0.0` поставляет актуатор GoBGP v4, ядро RFC 5880, одношаговый режим RFC 5881 на нумерованных multiaccess-интерфейсах, многошаговый режим RFC 5883, общие интервалы RFC 7419 и защиту локального управления по умолчанию. Echo (RFC 9747), Unsolicited BFD (RFC 9468), Micro-BFD (RFC 7130), VXLAN BFD (RFC 8971) и Geneve BFD (RFC 9521) сохраняют статус preview или experimental согласно [матрице покрытия RFC](../08-rfc-compliance.md). Пользователи, которым требуется GoBGP v3.37.0, остаются на ветке `release/v0.6`.

## Альтернативы

| Альтернатива | Причина отказа |
|:---|:---|
| Глобально повысить или отключить порог `10%` для `sec/op` | Ослабляет обнаружение регрессий в pull request и сопровождении `v1.0.x` |
| Заменить `previousPublishedRelease` статическим файлом без парного замера | Нарушает контракт парного измерения на одном runner в `release_benchmark.go` |
| Удерживать `release/v1.0` в канале `1.0.0-alpha.N` | Противоречит решению сопровождающего о выпуске `1.0.0` как новой ветки под GoBGP v4 |

## Последствия

- Выпуск `v1.0.0` прозрачно сравнивается с `v0.6.4` при первом прогоне `release.yml`, сохраняет полный комплект отчётов `comparison-vs-baseline.*` внутри `gobfd-1.0.0-reports.tar.gz` и автоматически становится строгой базой `critical` для `v1.0.1` и `v1.1.0`.
- Публикация стабильного `v1.0.0` переводит псевдонимы GHCR `:latest` и `:debian-trixie` на линию с GoBGP v4; при эксплуатации GoBGP v3 необходимо явно закреплять `0.6.4` или ветку `release/v0.6`.
- Длительные 24-часовые soak-испытания и проверки на внешних аппаратных NOS учитываются отдельно как эксплуатационные материалы без блокировки выпуска ветки `1.0.0`.
